Moved from CLAUDE.md on 22 Nov 2026 (Phase 6a run 7, step 0), word for word. These rules apply exactly as they did there; CLAUDE.md points here.

M7b wins for the outside Health Check. Checked against M7b itself, part by part to half a pixel and word for word, by `tests/healthcheck/compare-m7b.mjs` (Desktop 1440 and Phone 390, dark and light; each meant difference is listed there with why), with the flows and measurements in `tests/healthcheck/flow.mjs`, twice the text size in `tests/healthcheck/text-size.mjs`, screenshots from `tests/healthcheck/shots.mjs`, and the rules in `tests/healthcheck/*.test.mjs`. 1. **The Health Check's screens are built once, from the shared parts**, in `src/pages/healthCheck` (`HealthCheckTool`: the guided screens and the results, a `GuidedTool` with `calm`; `HealthCheckResults`: the one-pager; `HealthCheckChart`; `ProjectList`; `GuideCard` and `GuidePanel`; `HealthCheckEye`; `ExampleReport`). Its words, steps and results model stay in `src/health-check/words.js`, `flow.js` and `example.js`. The outside page is still its own bundle, left to the network by the service worker; it loads the portal's own styles and fonts (`src/globalStyles.js`), trimmed at build time to the rules and tokens its own code can use (`scripts/build/trimStyles.mjs`, in its own build pass; follow-up 1: first load 222 KB to 189 KB compressed; `CLARITY_NO_TRIM=1` builds without it), and follows the device's light or dark. A class it builds in code must keep a fixed start ending in `-` or `_` (`hc-dot--${state}`), or the trim can't see it; the comparison suites run against a production build (`APP_URL`, `tests/phase4/serve-build.mjs`) check it.
2. **Success Factors, never Critical Success Factors, and no abbreviation** (Tim, 14 Nov, 09:38), capitalised as a named part: "Success Factor 1 of 4", "Add a Success Factor", "How much does each Success Factor matter to your objective?", "It doesn’t move this Success Factor.", the question topic "Success Factors". Labels only: stored keys (`csfs`, `contrib`, `level`), step names and code names keep theirs, and a Health Check saved in the old wording opens and reads in the new words. 12. **Guests choose who sees their answers (Tim, 14 Nov, 09:49 and 09:52).** This replaces the 27 Oct rule that a guest's answers always go to the coach. The eye on every guest tool (the outside Health Check, Get unstuck's guest pages and every later guest tool) is the shared `GuestEye` (`HealthCheckEye` is the Health Check's name for it): "Only you" or "You and {coach's first name}" ("your coach" when the link doesn't name one), **You and Tim the default**, with the line under the choice from one function (`sharingLine` in `src/lib/guest/sharing.js`): "Tim sent you the link and will see your results." or "Tim won’t see your answers, but you still get your PDF." Switching back to You and Tim after finishing sends the coach's email then, once. **Only you means only you (migration 045; follow-up 1, 15 Nov):** the coach was given the access code with the link, so the first Only you replaces it at once with a new code, emailed to the guest's own address only (`api/_routes/alignment-email.js` kind `code`, `alignment_new_code_to_send`, the server's key; never returned to the browser), and the old code opens, saves and switches nothing from that moment. The page sends whatever waits first, then asks for the new code on the email and code screen ("We’ve emailed you a new access code, so only you can open your answers. Type it to carry on.", with "Didn’t get it? Send it again"; on a preview, which never emails, "Your access code has changed…", and `supabase/manual/alignment_new_code_on_test.sql` shows it on the test project). From then on switching needs the guest's code and makes no second one. While the new code waits, the replaced code answers `new_code` everywhere ("Your access code has changed. Check your email for the new one."), so a page whose own change's answer was lost, a second tab, or a link opened again later asks for the new code with "Didn’t get it? Send it again" instead of a dead end; an email that didn't go says so ("…the email with the new one didn’t go. Send it again to carry on."). Guests who chose Only you before 045 ran get a new code when it runs (`_alignment_reissue_private`). Proved at the database by `supabase/045_health_check_new_code_test.sql` and in the browser by `tests/healthcheck/sharing.mjs` (parts 5 to 7). A coach who switches to Only you first, with the code they were given, only shuts themself out: the new code still goes to the guest. Before 044 has run, or while the connection is away, the choice is kept on the device (`clarity-share:*`: the outside Health Check in localStorage, so the link opened in a new tab knows it, and another open tab's eye follows; a guest page's visit in sessionStorage), said as "Will sync" when it is the connection, sent when the connection is back, the coach's completion email is not asked for while it is Only you, nothing alarming is said, and it is sent once the function answers. The choice moves with the work into an account: `guest_claim` writes it into each saved item, and `alignment_claim` (asked once after each sign-in with `guest_claim`, `src/lib/guest/claim.js`) moves each finished outside Health Check of the account's own confirmed email into the account as an inside version (its team named from the organisation, or "My team", joining the team of that name when there is one; `from_outside` set, so Your teams shows its one-off tip). No coach Guests page exists yet, so "finished, but can't open" is proved at the database (`supabase/044_guest_sharing_test.sql`, `tests/rules/`).

### Inside the portal (mock-up M7, version 8.2; Tim, 13 and 14 Nov)

M7 wins for the Health Check inside the portal. Checked against M7 itself by `tests/healthcheck/compare-m7.mjs` (Desktop 1440 and Phone 390, dark and light), with the flows and measurements in `tests/healthcheck/inside-flow.mjs` (signed in as the test client; the Health Check's own reads and writes answered by a stand-in holding M7's teams, `tests/healthcheck/inside-shared.mjs`, and one real save that deletes itself) and the model in `tests/healthcheck/inside.test.mjs`.

14. **One address, `/strategic-alignment`** (`src/pages/healthCheckInside`): Your teams; `/example`; `/new?team=<id>` (a new version, or that team's draft); `/new-team`; `/version/<id>` (its results, or its questions while it is being made or edited); `/compare?team=&a=&b=`. The seven older pages (`/goal-setting` to `/project-scatter`) are gone: their addresses redirect here with query, hash and state (`RENAMED`), and a saved Health Check handed over in the state (`decisionId`, also from `/decision-summary`) opens that version. The portal's older outside route `/health-check/:token` is untouched.
15. **Kept with no migration** (`src/lib/healthCheck/inside.js`): one `decisions` row per version, tool type `strategic-alignment`, its title the team's name, `form_data` `{ shape: 2, team: { id, name }, date, made, from, data (the outside's saved shape), step (a draft's place), shared_with_coach, from_outside? }`, through the offline queue, the typing on the device until saved ("Draft restored"). The older pages' rows (`goal`, `factors`, `projects`, `matrix`, `progress`) open as a team named by the title with one version (`draftFromOld`: a contribution never set reads None, a progress never moved Fair, as those pages showed it; resource never asked reads "Not rated"), and are written in the new shape only when the person changes something (their `risks` and `strategies` kept).
16. **Your teams**: the title with play then the eye; **one first-visit message at a time**: the Quick guide's offer row (`OfferRow` with `useOffer('health-check-guide')`, rule 8b; while it shows the play icon hides; "Your teams, a later visit" adds Don’t show this again) first, then the one-off tip (`OneOffTip`) for a version marked `from_outside`, "Your April Health Check, done outside the portal, is now with the Leadership team.", closed for good on the device. Each team is a section with its finished versions newest first (`VersionRow`: "October Health Check", its headline, its date) and one quiet link, "Start a new version" ("Carry on with my new version" while one is being made). "Add another team" is the one add button; with no teams, the calm card "Which team’s work would you like to check against its strategy?" with the coral "Start a Health Check", and "See an example report". The eye here sets who sees every Health Check.
17. **A version's results are a page in the portal frame**, word for word the outside one-pager, then **Versions** after Questions to start with: "Start a new version" and, with two or more, "Compare two versions" (it lives only here). The title's meta is the team and the version's date. "Download my PDF" is the one coral button, in a bottom bar of its own (`BottomBar`): the phone bar steps back while it shows (`useHidePhoneBar`). The PDF carries the team's name. A quiet "Delete this version" and "Delete this team" (M7 draws none; "Deleted" with Undo).
18. **A new version carries the last version's answers with every rating blank** (M7 version 8.2's script and note): the objective, the Success Factors with their levels, the projects with their dates (the same ids) and the line; "Let’s start from your last answers." with the eye, "Start my new version". **A new team** asks "Which team is this Health Check for?" first ("Type the team’s name to carry on."; a name already used says so). Closing part-way keeps a draft ("Saved"); a new team with nothing but its name is let go (M7). Home's "Carry on where you left off" offers the version being made on the device.
19. **Compare two versions**: the version names only in the two drop-downs; choosing a later version older than the earlier swaps them; one sentence, never a figure, then the counts; the chart (each dot where it is now, a dashed ring and a fine line from where it was, at its size then) before How progress moved (rises first, in mint); Projects added and removed; no coral button. "Talk it through with Tim" shows only where the coach's chat is set up (`useStartChat`).
20. **The eye inside** offers "Only you" or "You and Tim", saved on the version there and then (`shared_with_coach`; no database rule lets a coach read `decisions` yet, so it is stored and shown only).
21. **Two tabs on one version never write over each other** (follow-up 1, 15 Nov). Each save is sent as "only if the version is still as this tab opened it, or as this tab last saved it" (the sync queue's `basedOn` with `guardRows`, which guards only the rows a page asks for, so every other tool's saves to `decisions` go as before). Refused: nothing is written, the tab's device copy goes back to the database's version, and it says "This version changed in another tab." with "Reload to see it" (never "Saved"; "Saved" after "Save my edit" shows only once the save has gone). The base is the version as its page opened it (a page left and opened again takes the newest), and the device's copy keeps the database's `updated_at`, never this device's clock. A version the database doesn't have yet is made "only if no other tab has made it". The queue on the device can be sent by any tab: each save carries its tab, and another tab's save is never counted as this tab's own or followed on from (`syncQueue.js`, `thisTab`). Checked by `tests/healthcheck/two-tabs.mjs` (with the break-it tester's offline, new-version and came-back cases). A page's own `BottomBar` lifts toasts 16px above it where its button runs under the middle of the screen, as a guided tool's does.

22. **The guest's own copy carries the results PDF, and results never close (follow-up 5; Tim, 25 Nov).** "Email my link" on a finished Health Check sends "Copy of a guest's answers" with the results PDF attached, made on the server from what `alignment_email_check` hands back (never from the browser; `api/_routes/alignment-email.js`, `api/_alignmentEmails.js`, `api/_pdfAssets.js` with the fonts in `pdf-fonts/`), and says "Your results are attached as a PDF, and you can open them again at any time with your link and code."; if the PDF can't be made the email still goes and doesn't say it is attached. An unfinished Health Check's email has no PDF and says it can be carried on. **The 30 days is only how long a link can be used to start a Health Check (rule of 27 Oct):** a guest sees their results at any time, kept 2 years after their last visit, with their link and code or by confirming their email. The results page keeps "We’ll email you a link, so you can find your results again at any time." The page waits for its saves to reach the database before asking for the email, so the PDF is of the finished answers.
